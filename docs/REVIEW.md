### ① 100% 더미 데이터가 화면에 "실데이터" 라고 표기된다 — 치명

브라우저를 띄우면 헤더 우측 배지에 **`실데이터`** 라고 뜬다 (스크린샷/DOM 텍스트로 확인).
그런데 실제로는:

- `apartment.json` / `apartment_sgg.json` / `apartment_sido.json` → `meta.sample = true`
- `poi_*.json` 4종 전부 → `meta.mode = "sample"`, `source = "SAMPLE(더미) — 실데이터 아님"`
- `metrics*.json` → `meta.sample = true`, `meta.sample_inputs = ["apartment.json", ...]`
  → **score / grade 전체가 더미 입력으로 산출된 값**

즉 화면에 보이는 **점수·등급·평당가·매매가·학원수·아파트 세대수가 전부 가짜인데,
대시보드는 그것을 "실데이터"라고 단언한다.** 실데이터는 인구와 경계뿐이다.

원인은 명확하다. `web/index.html` 의 `updateBadge()` 는 **`web/mock/` 폴더로 폴백했는지**만
본다(`state.usedMock`). `data/processed/` 에 파일이 **존재하면** 그 파일의 `meta.sample`
플래그가 `true` 여도 무조건 "실데이터"로 표기한다.
`index.html` 전체에서 `meta.sample` / `confidence` / `coverage` / `gated` 를 참조하는 코드는

### ③ 점수 산식이 대외 방어 불가 — 치명

`docs/SCORE.md` §4-1 은 **"대시보드는 confidence 를 반드시 함께 표기해야 한다"** 고
명시적으로 요구한다. 대시보드는 이를 **전혀 표기하지 않는다.** 그 결과:

- **송파구 95.0(S) > 강남구 86.6(S) > 서초구 59.9(B)** 가 화면에 그대로 노출된다.
- 팀장 재계산으로 원인을 확정했다. `score_parts` 를 직접 뜯어보면:
  - 송파구: `{size_pop 98.0, size_trend 79.7, power_price 98.8, power_hh 98.8}` — **경쟁강도 축이 아예 없음**(coverage 0.55)
  - 강남구: `{... comp_academy 66.7, access_school 100.0}` (coverage 1.0)
  - 서초구: `comp_academy 33.3`, **`access_school 0.0`** → 59.9점 = **B등급 "조건부 검토"**
- 더 심각한 건 **경쟁강도 백분위의 모집단이 4개뿐**이라는 점이다. POI가 있는 시군구가
  강남·서초·분당·부산강서 4곳뿐이라 `comp_academy` 는 사실상 **4개 중 몇 등**이다.
  서초 33.3 / 강서 0.0 / 분당 100.0 은 통계량이 아니라 4개짜리 순위표다.
  이 값이 전국 백분위인 것처럼 30% 가중치로 들어간다.
- 정량 확인: 행정동 평균점수 **high 64.2 (n=71) / mid 50.0 (n=3,132) / low 44.1 (n=419)**.
  근거가 많을수록 점수가 높아 보이지만, S등급 분포는 정반대다 —
  **S등급 178개 중 high는 3개뿐, 175개가 mid/low**(경쟁강도 미반영 지역).

"서초구가 조건부 검토(B)이고 평택시가 최우선(91.8 S)"이라는 화면을 상담에서 방어할 방법은 없다.
SCORE.md 의 설계 논리 자체는 훌륭하지만(§4-1/§4-3의 결측 처리, §4-2 게이트, §6 한계 고지),
**문서가 스스로 경고한 왜곡이 화면에서 가드 없이 그대로 노출**되고 있다.

### 3-9. 계약 외 추가 필드 판정

팀원들이 계약에 없는 필드를 다수 추가했다. **팀장 판단: 대부분 계약을 개정해 정식 채택할 가치가 있다.**

| 필드 | 위치 | 판정 |
|---|---|---|
| `confidence`, `coverage` | metrics | **채택 권고 (필수화)** — 상담 자료에서 근거 두께 표시는 필수다. 오히려 계약이 빠뜨린 것 |
| `score_parts` | metrics | **채택 권고** — "왜 이 점수인가"를 상담에서 설명 가능하게 한다. 방어력의 핵심 |
| `gated`, `no_academy` | metrics | **채택 권고** — SCORE.md §4-2/§4-3 과 대응. 산식 투명성 |
| `name`, `population`, `preschool`, `trend_pct`, `households`, `new_ratio` | metrics | **채택** — 대시보드가 실제 사용, 파일 간 재조인 비용 절감 |
| `meta.sample`, `meta.sample_inputs` | apartment/metrics | **채택 권고 (필수화)** — 이 프로젝트 최대 리스크의 유일한 방어선 |
| `meta.coverage_vs_code_map`, `meta.legacy_conversion` | population | **채택 권고** — 자기신고형 품질 메타. 모범 사례 |
| `code_legacy_map.json` 전체 | processed | **계약에 명시 추가 필요** — 계약 §2 에 파일 자체가 없다 |
| `bjd2adm_draft` | code_map | **조건부** — 미완성물이 SSOT 파일에 들어가 있다. `_draft` 접미사로 구분은 되나, 계약에 "draft 는 조인에 쓰지 않는다"를 명문화해야 한다 |
| `mode: "sample"` (poi) | poi | **채택하되 명명 통일 필요** — apartment/metrics 는 `sample: true`, poi 는 `mode: "sample"`. 대시보드가 **두 규격을 다 검사해야 하므로** 한쪽으로 통일할 것 |

> **계약 외 필드 자체는 문제가 아니다.** 문제는 **`metrics.confidence` 와 `meta.sample` 이
> 계약에 없다는 이유로 대시보드가 무시해도 되는 것처럼 취급된 것**이다.
> 계약 개정으로 이들을 필수 필드 + 필수 표기 대상으로 승격해야 한다.
